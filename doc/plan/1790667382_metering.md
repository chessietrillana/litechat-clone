# Plan: metering

Based on: `doc/study/1790660517_litechat-core.md` (build order item 7; section 9; NOTEs on Q5–Q10, Q14–Q16, Q28).

Goal:

- Every successful turn is charged to the session's billing account.
  - The cost is the input tokens plus the output tokens the proxy reports, times the model's tier price (NOTEs Q5, Q8).
- Each charge stores the price it used (NOTE Q10).
- The chat page shows the tokens and cost of each reply and of the whole session.
- Sending is blocked when the account's balance is 0 or less (NOTE Q14–15).
- A simple read-only **Usage** page lists the user's charges (NOTE Q28).

**Not in this plan:** rename and delete (hide) sessions. Those are plan 8.

Branch: `feat/metering`. The plan file is committed on this branch, as asked, and not on `main`.

## What exists now

- Packages: Django 5.2.17, python-dotenv 1.2.3. Nothing new is needed.
- `billing`:
  - `LedgerEntry` has `account`, `amount_micro` (µc, positive adds credits), `kind` (`signup_grant`, `admin_grant`), `note`, `created_by`, `created_at`.
  - Balance = the sum of an account's entries. `BillingAccount.objects.for_user(user).with_balance()`.
  - `TierPrice` has one row per tier, `price_per_1k_tokens` (credits, 3 decimals). `micro_per_token` gives an exact whole number of µc per token.
  - Seeded prices: Value 1, Standard 3, Premium 10 credits per 1K tokens (NOTE Q6).
  - The `credits` template filter formats µc as credits.
- `chat`:
  - `ChatMessage` saves `input_tokens`, `output_tokens`, `cached_tokens` on each reply. They are empty when the proxy sent no usage.
  - `chat/services.py` calls the proxy outside any transaction. Then it saves the user message and the reply in one `transaction.atomic()`.
  - An empty reply raises `ChatError` and nothing is saved.
  - `check_can_send` checks that the model is active and that the user may still use the account.
- No usage page. The header has **Models**, the username, and **Log out**.

## Decisions made in this plan

- **A charge is a ledger entry.** Balance stays "the sum of the entries", so it needs no other change.
  - New `LedgerEntry.Kind.CHARGE` (`charge`). `amount_micro` is negative (or 0 if the price is 0).
  - New fields on `LedgerEntry`, set on charges only:

    | Field | Notes |
    |---|---|
    | `tokens` | The tokens billed: input + output. |
    | `price_per_1k_tokens` | The tier price used, copied from `TierPrice` (NOTE Q10). Later price changes don't touch old charges. |

  - `created_by` is the user who sent the message. On a shared account, this tells members' charges apart.
  - A database check: a charge has `tokens` and a price and an amount ≤ 0. Other kinds have neither.
- **The link from a reply to its charge lives on the chat side:** `ChatMessage.charge`, a one-to-one link to `LedgerEntry` (empty when not charged).
  - `chat` already depends on `billing`. A link the other way would make the two apps depend on each other.
  - Deleting a message never deletes its charge. Charges stay forever (NOTE Q21, and plan 8).
- **How a turn is charged:**
  - Tokens = `input_tokens + output_tokens`, as the proxy reports them. The ~170 hidden tokens are included (NOTE Q8). If only one count is reported, the other counts as 0.
  - Cost (µc) = tokens × `micro_per_token`. Exact whole numbers. No rounding, no floats.
  - **Cached tokens cost the same as normal input tokens (NOTE Q9, your review).**
    - OpenAI `prompt_tokens` and Google `promptTokenCount` already include cached tokens.
    - Anthropic `input_tokens` does not. So the Anthropic adapter adds `cache_read_input_tokens` and `cache_creation_input_tokens` to it.
    - Result: `ChatResult.input_tokens` means "all input tokens, cached included" on every interface. Metering just uses it. `cached_tokens` stays as the cache reads, for information.
    - This is done in `proxy/adapters/anthropic.py`, so the saved `ChatMessage.input_tokens` and the log line match what is billed.
  - **No usage reported, no charge** (NOTE Q16). The reply is still saved and shown, with no charge.
  - **Failures are never charged** (timeout, error). Nothing is saved, as today.
- **The price is read before the proxy call.**
  - If the tier has no price row, the send is refused with "This model has no price set. Please tell the site admin." No request is made. This should not happen: the prices are seeded and the admin can't delete them.
  - The charge uses the price from the moment the message was sent. An admin price edit during the 30-second wait does not change it.
- **One transaction** (your decision): the user message, the reply, the ledger entry, and the link are saved together or not at all.
- **Empty replies with usage are saved and charged** (your decision, NOTEs Q8, Q16).
  - Today an empty reply raises `ChatError` and nothing is saved. Now:
    - Empty reply **with** usage: the turn is saved and charged. The page redirects as normal.
    - Empty reply **without** usage: nothing is saved and nothing is charged. The error shows, as today.
  - The proxy refuses empty messages in the history. So `session.history()` leaves out every turn whose reply is empty: both the user message and the empty reply. The history keeps going user, assistant, user, assistant.
  - The empty reply shows in the chat as a bubble with a note: "The model sent an empty reply. The tokens it used were charged. This turn is left out of later messages to the model."
  - The user's message leaves the input box, since the turn was saved. It is still in the thread, so the user can copy it and send it again.
- **Blocking at a balance of 0 or less** (NOTE Q14–15):
  - `check_can_send` also checks the balance before the proxy call. At ≤ 0, it refuses with "This billing account has no credits left. Ask an admin to add credits, or start a new chat with another account."
  - It applies to the new chat form and to sending in a session.
  - **A turn can take the balance below 0** (your decision). The cost is only known after the reply arrives. So a send at 0.5 credits can end at −2 credits. Then the next send is blocked.
  - The session page says so, next to the balance: "A reply's cost is known only after it arrives, so one reply can take the balance below 0. Then sending stops until an admin adds credits." The Usage page says the same.
  - When the account is at ≤ 0, the session page shows that note in place of the input box. The server still checks on every send, for a tab left open from before.
  - The new chat form still lists accounts at ≤ 0, with their balance. Picking one shows the error, and the text is kept.
- **Usage and cost per session** (session page):
  - Under each reply: "183 in · 12 out · 0.585 credits". With no usage reported: "No usage reported · not charged".
  - In the header: the session's total tokens and cost, and the account's current balance. For example: "GPT-5.6 Luna (Premium) · billed to alice (personal), balance 998.1 credits · this chat: 1,950 tokens, 19.5 credits".
  - On a shared account, the balance includes other members' use. The page says "shared" in the account name already.
- **The Usage page:**

  | URL | Name | What |
  |---|---|---|
  | `/usage/` | `usage` | Login needed. Read only. |

  - Lives in the `billing` app: `billing/urls.py`, `billing/views.py`, `billing/templates/billing/usage.html`. Uses the normal narrow page layout, like **Models**.
  - Top: "Your billing accounts", each with its balance. Plus the "can go below 0" note.
  - Below: "Your charges", newest first. Columns: Date, Chat (title, linked), Model, Account, Tokens (in / out), Price per 1K, Cost.
  - Only charges the user made (`created_by`). On a shared account, other members' charges are not shown. Their use still shows in the balance.
  - 50 rows per page, with **Newer** and **Older** links. Django's built-in `Paginator`.
  - With no charges: "No charges yet."
  - A **Usage** link goes in the header, next to **Models**.
- **Admin:**
  - Ledger entries: the list and detail pages show the tokens and price. Filter by kind already covers charges. Grants work as today. Charges can't be added, changed, or deleted in the admin.
  - Chat session page: the message inline shows each reply's cost.
- **Things that stay the same:** the proxy client, the 30-second timeout, no retries, the grant form, sign-up credits.

## Review points (answered)

- **Cached tokens on the Anthropic interface.** Answer: follow Q9. On Anthropic, cache reads and cache writes are added to the billed input tokens (see "How a turn is charged"). Tested, and recorded in a footgun.
- **Users with charges can't be deleted.** `created_by` is protected, like today's personal account entries. This already blocks deleting a user whose personal account has entries. It now also covers members of shared accounts who made charges. Answer: keep it. Charges stay forever.
