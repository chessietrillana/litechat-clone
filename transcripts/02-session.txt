  We are building a Litechat clone: a web app that gives regular users metered, 
  pay-as-you-go access to LLMs from several providers, so they don't need an    
  upfront, paid subscription to access them.                                    
                                                                                
  Stack: Python 3.11, Django 5.x, SQLite, Django built-in auth and admin,       
  server-rendered templates, no frontend framework. Use the venv in ./venv.     
  Follow CLAUDE.md.                                                             
                                                                                
  LLMs come from a proxy at https://proxy.litechat.ai with three interfaces:    
  OpenAI Chat Completions (/openai/v1), Anthropic Messages (/anthropic), and    
  Google Gemini (/google). Keys are already loaded as environment variables     
  named PROXY_OPENAI_KEY, PROXY_ANTHROPIC_KEY, and PROXY_GOOGLE_KEY (also       
  stored in .env). Never read or print .env or the keys. Docs:                  
  https://proxy.litechat.ai/docs                                                
                                                                                
  Core features:                                                                
  1. Users can sign up, log in, and log out of the site.                        
  2. Users start a new chat session by picking a model and a billing account.   
  Users can then chat, and the full history is sent to the model each turn.     
  3. Sessions are saved and listed in a sidebar; users can rename, reopen, and  
  delete them.                                                                  
  4. Metering: usage is metered per session. Each session is charged to the     
  billing account selected when it was started.                                 
  5. Models are listed with their provider and a tier (Value, Standard,         
  Premium).                                                                     
                                                                                
  Out of scope for now: real payments, streaming, file uploads, web search,     
  Google login, deployment.                                                     
                                                                                
  I may add to or change these core features later.

⏺ I wrote the proxy client plan and committed it as bf8f564 docs: plan proxy 
  client (doc/plan/1790662553_proxy-client.md). It isn't pushed yet.

  What it builds: a single function, send_chat(interface, model, history, 
  max_tokens=None, system=None). It returns the reply text, input, output and
  cached token counts, a normalized finish reason (stop, length, filtered,
  tool_call or other), and the response ID. When something goes wrong it raises
  a named error instead. The chat plan will call it later. There's no UI,
  database table or billing in this plan.

  Steps. The work runs on a new branch, feat/proxy-client, with one commit per
  step:
  1. feat: add proxy app with HTTP transport and errors: a new proxy app, a
     30-second timeout, never retries, and 8 error types, each with a short
     message the chat page can show as is.
  2. feat: add OpenAI chat completions adapter
  3. feat: add Anthropic messages adapter
  4. feat: add Google generateContent adapter
  5. feat: add send_chat proxy client: checks the key and the history, calls the
     proxy, turns error codes into the right error, and logs one line per call.
  6. feat: add proxy_smoke management command: a live test against the real
     proxy that you can run by hand. I'll run it once at the end and report the
     results.
  7. docs: record proxy client footguns, only if something surprising comes up.

  Steps 2–4 are tested against the real sample responses from the study. Replies
  I never captured get hand-written samples named synthetic_*, such as cut-off
  replies, errors other than 401, and a blocked Google prompt. No test touches
  the network.

  Credit unit: micro-credits (1 credit = 1,000,000 µc), stored as whole numbers.
  - At the Value price, one token costs 0.001 credit, so the unit has to be at
    least that small.
  - Milli-credits (1/1000) would stop being exact as soon as an admin set a
    price like 1.5 or 0.25 credits per 1K tokens.
  - With micro-credits, any price with up to 3 decimals is a whole number of µc
    per token. So every charge is tokens × price per token, which is exact, with
    no rounding and no floats.
  - Nobody sees µc. Admins type credits, and pages show credits like 1,000 or
    999.817.
